SERFAGAB — Guía de Cambios: Paginación y Órdenes por Fecha (Grupo 5)

Última tanda de mejoras: paginación en Materiales, Proveedores y Tipos de Material (al estilo de Órdenes de Compra) y listado de órdenes en orden descendente por fecha, para que una orden recién creada sea la primera que se vea.

Backend: Spring Boot 4 (Java 24) + MySQL · Frontend: Angular 21 + Bootstrap 5 · Tamaño de página: 5 registros · Orden de listados: por ID ascendente

1. Resumen rápido BACKEND FRONTEND

1 Paginación en Materiales (nombre, descripción, tipo) NUEVO Backend /api/materiales/paginado + componente
2 Paginación en Proveedores (razón social, RUC, email) NUEVO Backend /api/proveedores/paginado + componente
3 Paginación en Tipos de Material (nombre, descripción) NUEVO Backend /api/tipos-material/paginado + componente

Resultado: los 4 listados del sistema ahora tienen el mismo comportamiento: 5 registros por página, botones « Anterior / Siguiente », indicador "Página X de Y (N registros)", y los filtros de búsqueda conviven con la paginación (buscar siempre vuelve a la página 1).

2. Backend: endpoints paginados BACKEND

a) Repositorios: overloads con Pageable NUEVO

Spring Data JPA permite sobrecargar un finder: si le pasas un Pageable, devuelve Page<T> (contenido + total de páginas + total de registros). Se agregaron las versiones paginadas de los finders que ya existían, sin tocar los originales:

b) Controladores: endpoint /paginado NUEVO

Cada controlador recibió un nuevo GET. Los endpoints anteriores (GET /api/materiales, /api/proveedores, etc.) siguen funcionando igual: el dashboard y los selects (combo de tipos al crear material, combo de proveedores en órdenes) los siguen usando.

// Materiales
GET /api/materiales/paginado?page=0&size=5&criterio=nombre|descripcion|tipo&texto=...&idTipo=...

// Proveedores
GET /api/proveedores/paginado?page=0&size=5&criterio=razonSocial|ruc|email&texto=...

// Tipos de material
GET /api/tipos-material/paginado?page=0&size=5&criterio=nombre|descripcion&texto=...

Lógica interna (igual en los tres):

  • Si texto viene vacío → devuelve todo el listado activo, paginado (findByActivoTrue(pageable)).
  • Si hay texto → filtra según criterio (en materiales, tipo usa idTipo).
  • El orden es por ID ascendente gracias a Sort.by("idMaterial").ascending() (y equivalentes), así cada página muestra siempre los mismos registros en el mismo orden.
  • La respuesta es un objeto JSON estándar de Spring: { content, totalPages, totalElements, ... }.
// Ejemplo (MaterialController.java)
@GetMapping("/paginado")
public Page<Material> listarPaginado(
        @RequestParam(defaultValue = "0") int page,
        @RequestParam(defaultValue = "5") int size,
        @RequestParam(defaultValue = "nombre") String criterio,
        @RequestParam(required = false) String texto,
        @RequestParam(required = false) Integer idTipo) {
    Pageable pageable = PageRequest.of(page, size, Sort.by("idMaterial").ascending());
    boolean hayTexto = texto != null && !texto.trim().isEmpty();
    // switch (criterio) ... devuelve la página correspondiente,
    // o findByActivoTrue(pageable) cuando no hay filtros
}
Nota sobre seguridad: como son GET bajo las mismas rutas ya cubiertas por SecurityConfig ("leer es libre"), no hizo falta cambiar nada de permisos.

c) Órdenes de compra: fecha descendente MEJORA

Antes el listado paginado (GET /api/ordenes-compra/usuario/{id}/paginado) no definía orden, así que las órdenes salían en el orden por defecto de la BD y una orden nueva quedaba "perdida" entre las últimas páginas.

// Antes
Pageable pageable = PageRequest.of(page, size);

// Ahora (OrdenCompraController.java - historialPaginado)
Sort sort = Sort.by(Sort.Order.desc("fecha"), Sort.Order.desc("idOrdenCompra"));
Pageable pageable = PageRequest.of(page, size, sort);
return ordenCompraRepository.buscarPaginadoConFiltros(idUsuario, estado, idProveedor, fechaDesde, fechaHasta, pageable);
  • fecha DESC: lo más reciente primero.
  • idOrdenCompra DESC como desempate: si dos órdenes tienen la misma fecha, la de mayor ID (creada más tarde) aparece primero.
  • El frontend ya volvía a la página 0 después de crear una orden, así que ahora la orden recién creada se ve inmediatamente arriba.
  • Los filtros (estado, proveedor, rango de fechas) siguen aplicando igual; solo cambia el orden.
  • El dashboard no se afecta: trae hasta 1000 órdenes y calcula pendientes en memoria.

3. Frontend Angular FRONTEND

a) Services: método listarPaginado() NUEVO

Los tres services sumaron un método que arma los parámetros con HttpParams y devuelve el objeto Page tal cual lo manda Spring:

// material.service.ts (equivalente en proveedor.service.ts y tipo-material.service.ts)
listarPaginado(page: number, size: number, filtros?: MaterialFiltros): Observable<any> {
  let params = new HttpParams().set('page', page).set('size', size);
  if (filtros) {
    if (filtros.criterio) { params = params.set('criterio', filtros.criterio); }
    if (filtros.texto)    { params = params.set('texto', filtros.texto); }
    if (filtros.idTipo != null) { params = params.set('idTipo', filtros.idTipo); }
  }
  return this.http.get<any>(`${this.apiUrl}/paginado`, { params });
}

b) Componentes TS: campos y navegación NUEVO

materiales.component.ts, proveedores.component.ts y tipos-material.component.ts replican el patrón de ordenes.component.ts:

  • Nuevos campos: page = 0, size = 5, totalPages, totalElements.
  • listar() ahora llama al endpoint paginado pasándole el criterio/texto actual y lee data.content, data.totalPages y data.totalElements.
  • buscar() reinicia a la página 0 antes de consultar (los resultados entran siempre por la primera página).
  • Nuevos métodos anterior() y siguiente(), idénticos a los de órdenes.
  • Al crear/editar se vuelve a la página 1; al eliminar, si era el único registro de la página, se retrocede una para no quedarse viendo una página vacía.
  • Búsqueda por ID: sigue siendo resultado único vía obtener(id); en ese caso se fija totalPages = 1 y los botones de paginación quedan deshabilitados.
  • Los criterios de búsqueda y placeholders dinámicos de la guía anterior ("Buscar por nombre..." / "Buscar por descripción..." / "Buscar por ID...") no cambiaron.

c) HTML: bloque de paginación VISUAL

Bajo la tabla de cada CRUD se agregó el mismo bloque que ya tenía órdenes:

<div class="mt-3">
  <button class="btn btn-secondary" (click)="anterior()" [disabled]="page <= 0">
    &laquo; Anterior
  </button>
  <span class="mx-3">Página {{ page + 1 }} de {{ totalPages }} ({{ totalElements }} materiales)</span>
  <button class="btn btn-secondary" (click)="siguiente()" [disabled]="page >= totalPages - 1">
    Siguiente &raquo;
  </button>
</div>

5. Qué probar DEMO

1
Paginación básica: entra a Materiales (27 registros → 6 páginas), Tipos (8 → 2 páginas) y Proveedores (16 → 4 páginas). Navega con Anterior/Siguiente y revisa el contador "Página X de Y (N registros)".
2
Filtros + paginación: en Materiales busca plancha por nombre (una sola página), cambia el criterio a Descripción y busca galvanizada, luego filtra por Tipo Cable electrico. En cada búsqueda la tabla vuelve a la página 1.
3
Búsqueda por ID: con criterio ID busca 12: debe aparecer solo ese material con la paginación deshabilitada.
4
Órdenes por fecha: abre Órdenes de Compra: la más reciente aparece primero. Crea una orden nueva: tras guardar vuelves a la página 1 y tu orden está arriba de todo.
5
Edge case: ubícate en la última página de cualquier CRUD y elimina el único registro de esa página: la vista retrocede automáticamente a la página anterior.
