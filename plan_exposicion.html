PRUEBA 1: Login exitoso

MétodoPOST http://localhost:8080/api/auth/login
Body (JSON)
{"login":"admin","clave":"123"}
Respuesta esperada200 OK + datos del usuario admin (Valerie Cavero, idTipo=1)
¿Por qué funciona? El AuthController recibe el JSON, lo convierte en un objeto LoginRequest (anotado con @RequestBody). Llama al repositorio UsuarioRepository.findByLoginAndClave(), que Spring Data JPA traduce automáticamente a WHERE login = ? AND clave = ?. Como el DataSeeder precargó al usuario admin/123, lo encuentra y lo devuelve. Si no lo encuentra, Optional.orElse(null) retorna null y responde con 401. 
// AuthController.java
@PostMapping("/login")
public ResponseEntity<?> login(@RequestBody LoginRequest loginRequest) {
    Usuario usuario = usuarioRepository
        .findByLoginAndClave(loginRequest.getLogin(), loginRequest.getClave())
        .orElse(null);
    if (usuario == null)
        return ResponseEntity.status(401).body("Credenciales invalidas");
    return ResponseEntity.ok(usuario);
}

// UsuarioRepository.java
public interface UsuarioRepository extends JpaRepository<Usuario, Integer> {
    Optional<Usuario> findByLoginAndClave(String login, String clave);
}

PRUEBA 8: Actualizar proveedor

MétodoPUT http://localhost:8080/api/proveedores/1
Body (JSON)
{"razonSocial":"Comercializadora Andina EIRL",
 "ruc":"20605478931","celular":"999999999",
 "email":"nuevo@andina.com.pe",
 "descripcion":"Actualizado","activo":true}
Respuesta esperada200 OK + datos actualizados (celular=999999999, email cambiado)
¿Por qué funciona? El método primero busca el proveedor por ID. Si existe, obtiene el objeto manejado por JPA (persistente) y actualiza sus campos con los del JSON recibido. Luego save(p) ejecuta un UPDATE. Como el objeto es persistente, JPA detecta los cambios automáticamente (dirty checking). 
// ProveedorController.java - actualizar
@PutMapping("/{id}")
public ResponseEntity<Proveedor> actualizar(@PathVariable Integer id,
        @RequestBody Proveedor proveedor) {
    return proveedorRepository.findById(id)
            .map(p -> {
                p.setRazonSocial(proveedor.getRazonSocial());
                p.setRuc(proveedor.getRuc());
                p.setCelular(proveedor.getCelular());
                p.setEmail(proveedor.getEmail());
                p.setDescripcion(proveedor.getDescripcion());
                p.setActivo(proveedor.getActivo());
                return ResponseEntity.ok(proveedorRepository.save(p));
            })
            .orElse(ResponseEntity.notFound().build());
}

PRUEBA 9: Crear orden de compra

MétodoPOST http://localhost:8080/api/ordenes-compra/1/crear
Body (JSON)
{"proveedor":{"idProveedor":1},
 "fecha":"2025-12-15",
 "observaciones":"Pedido urgente"}
Respuesta esperada200 OK + orden creada con estado "PENDIENTE", total=0.0
¿Por qué funciona? OrdenCompraController.crear() recibe el idUsuario=1 desde la URL y extrae el proveedor del JSON. Delega en OrdenCompraService.crearOrden(), que: 1) busca Usuario y Proveedor por ID, 2) crea una nueva OrdenCompra con estado "PENDIENTE" y total 0.0, 3) la guarda. La anotación @Transactional asegura que todo se ejecute en una sola transacción. 
// OrdenCompraService.java - crearOrden
@Transactional
public OrdenCompra crearOrden(Integer idUsuario, Integer idProveedor,
        LocalDate fecha, String observaciones) {
    Usuario usuario = usuarioRepository.findById(idUsuario).orElseThrow();
    Proveedor proveedor = proveedorRepository.findById(idProveedor).orElseThrow();
    OrdenCompra orden = new OrdenCompra();
    orden.setUsuario(usuario);
    orden.setProveedor(proveedor);
    orden.setFecha(fecha);
    orden.setEstado("PENDIENTE");
    orden.setTotal(0.0);
    orden.setObservaciones(observaciones);
    return ordenCompraRepository.save(orden);
}

PRUEBA 10: Agregar detalle a la orden (x2)

MétodoPOST http://localhost:8080/api/ordenes-compra/1/agregar-detalle
Body 1
{"material":{"idMaterial":1},
 "cantidad":10, "precioUnitario":5.00}
Respuesta 1200 OK + detalle creado con subtotal=50. Total de OC actualizado a 50.
Body 2
{"material":{"idMaterial":2},
 "cantidad":5, "precioUnitario":8.00}
Respuesta 2200 OK + detalle con subtotal=40. Total de OC ahora = 90.
¿Por qué funciona? agregarDetalle() en el Service: 1) busca la orden y el material por ID, 2) calcula subtotal = cantidad * precioUnitario, 3) crea y guarda el DetalleOrdenCompra, 4) acumula el subtotal al total de la orden y la vuelve a guardar. Esto demuestra la lógica de negocio: cada detalle actualiza el total de la orden automáticamente. 
// OrdenCompraService.java - agregarDetalle
@Transactional
public DetalleOrdenCompra agregarDetalle(Integer idOrden, Integer idMaterial,
        Double cantidad, Double precioUnitario) {
    OrdenCompra orden = ordenCompraRepository.findById(idOrden).orElseThrow();
    Material material = materialRepository.findById(idMaterial).orElseThrow();
    Double subtotal = cantidad * precioUnitario;
    DetalleOrdenCompra detalle = new DetalleOrdenCompra();
    detalle.setOrdenCompra(orden);
    detalle.setMaterial(material);
    detalle.setCantidad(cantidad);
    detalle.setPrecioUnitario(precioUnitario);
    detalle.setSubtotal(subtotal);
    detalleRepository.save(detalle);
    orden.setTotal(orden.getTotal() + subtotal);  // acumula al total
    ordenCompraRepository.save(orden);
    return detalle;
}

PRUEBA 13: Registrar materiales por lote

MétodoPOST http://localhost:8080/api/materiales/lote
Body (JSON)
[{"nombre":"Tornillo 5mm",
   "unidadMedida":"unidad",
   "stockActual":100,
   "precioReferencial":0.50,
   "tipoMaterial":{"idTipoMaterial":1}},
  {"nombre":"Pintura Blanca",
   "unidadMedida":"galon",
   "stockActual":20,
   "precioReferencial":45.00,
   "tipoMaterial":{"idTipoMaterial":2}}]
Respuesta esperada200 OK + "Materiales registrados satisfactoriamente."
¿Por qué funciona? El controller recibe un array JSON que Spring convierte en List<Material>. Delega en MaterialService.registrarLote(), que hace batch insert: itera los materiales, los persiste con em.persist() y cada 10 inserciones hace flush() y clear() para liberar memoria. Esto es clave cuando se importan muchos materiales. 
// MaterialService.java - registrarLote
@Transactional
public void registrarLote(List<Material> materiales) {
    int i = 0;
    for (Material m : materiales) {
        em.persist(m);
        i++;
        if (i % 10 == 0) { em.flush(); em.clear(); }
    }
}

MétodoGET http://localhost:8080/api/ordenes-compra/1

¿Por qué funciona? findById(1) obtiene la orden. // OrdenCompraController.java
@GetMapping("/{idOrden}")
public ResponseEntity<OrdenCompra> detalle(@PathVariable Integer idOrden) {
    return ordenCompraRepository.findById(idOrden)
            .map(ResponseEntity::ok)
            .orElse(ResponseEntity.notFound().build());

// OrdenCompra.java (fragmento)
@OneToMany(mappedBy = "ordenCompra", cascade = CascadeType.ALL, orphanRemoval = true)

3. Recomendaciones para la exposición
  • PPT (Valerie): Enfocarse en el problema de SERFAGAB (registro manual) y cómo la solución web lo resuelve. No profundizar en código en el PPT, eso viene en las pruebas.
  • Pruebas Postman: Tener Postman abierto y la colección lista. Mostrar primero el JSON de entrada, luego enviar, luego mostrar la respuesta. Explicar brevemente el fragmento de código asociado.
  • Errores comunes: Si la aplicación no responde, verificar que esté corriendo (mvn spring-boot:run). Si los datos seed no aparecen, revisar que ddl-auto=create esté en application.properties.
  • Consola H2: Mostrar opcionalmente en http://localhost:8080/h2-console para verificar que los datos se persisten en memoria.
  • Preguntas frecuentes del docente:
    • ¿Cómo Spring Boot sabe qué SQL ejecutar? → Spring Data JPA interpreta los nombres de los métodos del Repository.
    • ¿Por qué no escribieron SQL? → JPA genera automáticamente las consultas según los nombres de los métodos.
    • ¿Cómo funciona @Transactional? → Agrupa varias operaciones en una sola transacción; si algo falla, se deshace todo.
