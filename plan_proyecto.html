1. Introducción — ¿Qué es SERFAGAB?

SERFAGAB S.A.C. es una empresa peruana dedicada a la comercialización de materiales industriales. Este proyecto consiste en construir una API REST que le permita gestionar sus Órdenes de Compra de manera digital.

El sistema permite:

  • Registrar y autenticar usuarios
  • Administrar proveedores
  • Gestionar materiales y sus tipos
  • Crear órdenes de compra con múltiples detalles (materiales, cantidades, precios)
  • Cambiar el estado de las órdenes (PENDIENTE → ENVIADO / ANULADO)
  • Consultar el historial de órdenes por usuario
Tecnologías: Java 24 · Spring Boot 4.0.7 · Spring Data JPA · Spring Security · MySQL · Lombok · Maven

2. Arquitectura general

El proyecto sigue el patrón MVC (Modelo - Vista - Controlador) adaptado para APIs REST, con una arquitectura en capas:

  ┌─────────────────────────────────────────────────────────────┐
  │                     Cliente (Postman)                        │
  │               (peticiones HTTP: JSON in / JSON out)          │
  └─────────────────────┬───────────────────────────────────────┘
                        │
                        ▼
  ┌─────────────────────────────────────────────────────────────┐
  │  CAPA CONTROLLER     (@RestController)                      │
  │  Recibe las peticiones HTTP, valida datos básicos,      │
  │  delega en Services o directamente en Repositories          │
  └─────────────────────┬───────────────────────────────────────┘
                        │
                        ▼
  ┌─────────────────────────────────────────────────────────────┐
  │  CAPA SERVICE        (@Service)                             │
  │  Contiene la lógica de negocio: crear órdenes,         │
  │  registrar lotes, calcular totales...                       │
  └─────────────────────┬───────────────────────────────────────┘
                        │
                        ▼
  ┌─────────────────────────────────────────────────────────────┐
  │  CAPA REPOSITORY    (extends JpaRepository)                 │
  │  Capa de acceso a datos. Spring Data JPA genera            │
  │  automáticamente las consultas SQL                      │
  └─────────────────────┬───────────────────────────────────────┘
                        │
                        ▼
  ┌─────────────────────────────────────────────────────────────┐
  │  CAPA ENTITY         (@Entity)                              │
  │  Mapea las tablas de la base de datos a objetos Java        │
  └─────────────────────────────────────────────────────────────┘
                        │
                        ▼
  ┌─────────────────────────────────────────────────────────────┐
  │  Base de datos MySQL                                        │
  │  (jdbc:mysql://localhost:3306/serfagab_db)                  │
  └─────────────────────────────────────────────────────────────┘

Flujo de una petición (ejemplo: login)

  1. Postman envía POST /api/auth/login con un JSON {"login":"admin","clave":"123"}
  2. AuthController recibe la petición y convierte el JSON en un objeto LoginRequest
  3. El controller llama a usuarioRepository.findByLoginAndClave()
  4. UsuarioRepository (interface que extiende JpaRepository) ejecuta automáticamente la consulta SQL: SELECT * FROM tbl_usuario WHERE login = ? AND clave = ?
  5. Si encuentra el usuario, lo devuelve; si no, responde con 401 (credenciales inválidas)
  6. Postman recibe la respuesta JSON con los datos del usuario

Detalle de cada entidad

Tipo

Define los roles de usuario. Por ahora solo existe "administrador".

@Entity @Table(name = "tbl_tipo")
public class Tipo {
    @Id
    private Integer idTipo;
    private String descripcion;
}

Usuario

Representa a una persona que usa el sistema. Tiene credenciales de acceso (login + clave) y pertenece a un Tipo (rol).

@Entity @Table(name = "tbl_usuario")
public class Usuario {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Integer idUsuario;
    private String nombres, apellidos, login, clave, email;
    private Boolean activo = true;
    @ManyToOne @JoinColumn(name = "id_tipo")
    private Tipo tipo;
}

@ManyToOne indica que muchos usuarios pueden tener un mismo Tipo. La columna id_tipo es la clave foránea.

Proveedor

Empresas que venden materiales a SERFAGAB. Contiene datos de contacto y RUC.

TipoMaterial

Categoría de materiales (ej: "Plancha", "Pintura").

Material

Producto individual que se puede comprar. Pertenece a un TipoMaterial y tiene unidad de medida, stock y precio referencial.

OrdenCompra

Documento que registra una compra a un proveedor. La crea un usuario, tiene fecha, estado y un total que se calcula sumando los subtotales de sus detalles. La relación @OneToMany con cascade = CascadeType.ALL significa que si se guarda una orden, automáticamente se guardan también sus detalles.

DetalleOrdenCompra

Cada línea de una orden de compra: qué material se compra, en qué cantidad, a qué precio unitario, y el subtotal (cantidad × precio). La anotación @JsonIgnore sobre ordenCompra evita que al serializar a JSON se genere un bucle infinito (la orden tiene detalles, y cada detalle tiene la orden...).

5. Recorrido por las capas del código

5.1 Punto de entrada: SerfagabApplication.java

@SpringBootApplication
public class SerfagabApplication {
    public static void main(String[] args) {
        SpringApplication.run(SerfagabApplication.class, args);
    }
}

@SpringBootApplication es un atajo que incluye:

  • @Configuration — permite definir beans
  • @EnableAutoConfiguration — Spring Boot configura automáticamente todo (Tomcat, JPA, H2, etc.)
  • @ComponentScan — escanea el paquete com.serfagab en busca de clases anotadas

5.2 Capa de persistencia: Repositorios

Los repositorios son interfaces que extienden JpaRepository<Entidad, TipoDeId>. Spring Data JPA implementa automáticamente los métodos, sin necesidad de escribir SQL.

public interface UsuarioRepository extends JpaRepository<Usuario, Integer> {
    Optional<Usuario> findByLoginAndClave(String login, String clave);
}

public interface MaterialRepository extends JpaRepository<Material, Integer> {
    List<Material> findByNombreContainingIgnoreCase(String nombre);
}

Spring Data JPA interpreta el nombre del método y genera la consulta: findByLoginAndClave se traduce a WHERE login = ? AND clave = ?. findByNombreContainingIgnoreCase genera WHERE UPPER(nombre) LIKE UPPER(CONCAT('%', ?, '%')), permitiendo búsquedas parciales sin distinción de mayúsculas. Optional<T> es un contenedor que puede o no tener valor, evitando errores de null.

5.3 Capa de servicio: lógica de negocio

MaterialService

Contiene el método registrarLote() que guarda varios materiales de una sola vez usando batch inserts. Cada 10 inserciones hace flush() y clear() para liberar memoria. Esto es útil cuando se importan muchos materiales desde un archivo.

@Transactional
public void registrarLote(List<Material> materiales) {
    int i = 0;
    for (Material m : materiales) {
        em.persist(m);
        i++;
        if (i % 10 == 0) { em.flush(); em.clear(); }
    }
}

@Transactional garantiza que si algo falla, se deshace todo (rollback).

OrdenCompraService

Tiene tres métodos principales:

  • crearOrden() — crea una orden vacía con estado PENDIENTE y total 0. Recibe el id del usuario, id del proveedor, fecha y observaciones.
  • agregarDetalle() — añade un material a una orden existente. Calcula el subtotal y lo acumula al total de la orden. Ambos métodos son @Transactional.
  • listarPorUsuario() — devuelve todas las órdenes de un usuario.

5.4 Capa de controladores: los endpoints REST

Cada controlador es un @RestController que expone endpoints. Veamos los más importantes:

AuthController

@PostMapping("/login")
public ResponseEntity<?> login(@RequestBody LoginRequest loginRequest) {
    Usuario usuario = usuarioRepository
        .findByLoginAndClave(loginRequest.getLogin(), loginRequest.getClave())
        .orElse(null);
    if (usuario == null)
        return ResponseEntity.status(401).body("Credenciales invalidas");
    return ResponseEntity.ok(usuario);
}

@RequestBody convierte automáticamente el JSON que envía Postman en un objeto LoginRequest. Si el usuario existe, se devuelve con código 200; si no, 401.

OrdenCompraController

Es el controlador más complejo. Gestiona la creación de órdenes, el agregado de detalles, el cambio de estado y la consulta de historial. Los endpoints:

  • POST /api/ordenes-compra/{idUsuario}/crear — recibe JSON con el proveedor y la fecha
  • POST /api/ordenes-compra/{idOrden}/agregar-detalle — recibe el material, cantidad y precio
  • PUT /api/ordenes-compra/{idOrden}/estado?estado=ENVIADO — cambia el estado
  • GET /api/ordenes-compra/usuario/{idUsuario} — historial

El patrón ResponseEntity.ok() / .notFound().build() / .badRequest().body(mensaje) permite controlar los códigos HTTP de respuesta (200, 404, 400).

7. Endpoints y pruebas en Postman

Requisitos antes de ejecutar

  1. MySQL corriendo (XAMPP): abre XAMPP y pulsa Start en MySQL (puerto 3306).
  2. Crear la base de datos: en phpMyAdmin crea la base serfagab_db (solo la BD, sin tablas). Las tablas las genera Hibernate al arrancar la aplicación gracias a ddl-auto=create.
  3. Ejecutar la aplicación: desde IntelliJ, pulsa "Play" en la clase SerfagabApplication (o mvn spring-boot:run). Arrancará en http://localhost:8080.
  4. Verificar: al arrancar se crean las tablas y el DataSeeder inserta los datos de prueba automáticamente.
Seguridad (agregada en la Fase 2): la API usa HTTP Basic con usuarios en memoria: admin/admin123 (rol ADMIN) y user/user123 (rol USER). En Postman, pestaña Authorization → tipo Basic Auth y coloca esas credenciales.

Rutas públicas (sin autenticación): /api/auth/login, /api/usuarios/**, /api/materiales/** y /api/tipos-material/**. Rutas protegidas: /api/proveedores/** (cualquier usuario autenticado) y /api/ordenes-compra/** (solo rol USER). Si pruebas las rutas protegidas sin credenciales obtendrás 401 Unauthorized.

Flujo completo de prueba (paso a paso)

  1. Login: POST /api/auth/login con admin/123 → obtienes el usuario con id=1
  2. Crear proveedor (opcional, ya hay 2 precargados)
  3. Crear tipo material (opcional, ya hay 2 precargados)
  4. Crear materiales (opcional, ya hay 2 precargados)
  5. Crear orden: POST /api/ordenes-compra/1/crear con proveedor=1
  6. Agregar detalles: POST /api/ordenes-compra/1/agregar-detalle varias veces
  7. Verificar: GET /api/ordenes-compra/1 → ves la orden con los detalles y el total calculado
  8. Cambiar estado: PUT /api/ordenes-compra/1/estado?estado=ENVIADO
  9. Historial: GET /api/ordenes-compra/usuario/1 → ves todas las órdenes del admin
