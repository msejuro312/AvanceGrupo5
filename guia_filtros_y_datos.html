1. Login con roles Spring Security

El problema original: la BD solo tenía un usuario sembrado (admin / 123) que nadie conocía, mientras Spring Security tenía usuarios internos distintos; y el frontend enviaba siempre credenciales fijas (user:user123) en todas las peticiones.

Solución: el DataSeeder siembra los dos usuarios oficiales con clave encriptada (BCrypt), el endpoint /api/auth/login valida contra la BD, y cada petición viaja con las credenciales del usuario real.

Credenciales (se crean automáticamente al arrancar el backend)

UsuarioClaveRol (tipo)Puede hacer
adminadmin123administrador Crear, editar, eliminar, cambiar estado de OC, ver PDF y dashboard
useruser123usuario Solo consultar: listados, filtros, detalles y PDF

Piezas del login

  • config/DataSeeder.java: crea tipos ADMIN(1)/USER(2) y los dos usuarios con passwordEncoder.encode(clave).
  • repository/UsuarioRepository.java: método findByLogin(login).
  • service/UsuarioDetailsService.java: carga el usuario de la BD y le asigna ROLE_ADMIN o ROLE_USER según su tipo. Es el puente entre la tabla tbl_usuario y Spring Security.
  • controller/AuthController.java: recibe JSON {login, clave}, busca el usuario y valida con passwordEncoder.matches(). Devuelve el usuario sin la clave o error 401. Registro público en /api/auth/registrar.
  • dto/LoginRequest.java: el DTO del body.

2. Reglas de acceso en el backend SecurityConfig

config/SecurityConfig.java define quién entra a cada endpoint. Regla general: leer es libre, escribir es solo del admin.

Método HTTPRutasQuién puede
GETmateriales, tipos-material, proveedores, ordenes-compraTodos (el rol user usa filtros y ve listados)
POST / PUT / DELETElas mismas rutasSolo ROLE_ADMIN
cualquiera/api/auth/**, /api/usuarios/**Libre (login y registro)

Autenticación HTTP Basic + BCrypt para comparar claves. Si un USER intenta crear/editar/borrar, el backend responde 403 Forbidden.

7. Placeholders dinámicos en los filtros CORREGIDO

a) El problema

En Materiales el input tenía el texto fijo "Buscar por nombre..." aunque cambiaras el criterio a ID o Descripción. Proveedores y Tipos de Material ya eran dinámicos; Órdenes no aplica porque sus filtros son selects y fechas (no tiene campo de texto).

b) La solución (binding dinámico)

<input *ngIf="criterioBusqueda !== 'tipo'" ...
       [placeholder]="criterioBusqueda === 'nombre' ? 'Buscar por nombre...'
                     : criterioBusqueda === 'descripcion' ? 'Buscar por descripción...'
                     : 'Buscar por ID...'" />

11. Cómo ejecutar desde cero

1
MySQL con XAMPP: Start a MySQL. Si además tienen el servicio Windows "MySQL80", deténello primero (services.msc → MySQL80 → Detener) porque ocupa el 3306 y genera "Access denied for user 'root'".
2
Crear la BD (una sola vez) en phpMyAdmin: CREATE DATABASE serfagab_db; — tablas, usuarios y datos de prueba los crea el backend.
3
Backend: abrir en IntelliJ y ejecutar. Esperar "Started SerfagabApplication" (Tomcat en 8080). Si sale "Port 8080 was already in use", otra instancia sigue corriendo: deténerla (botón Stop rojo) o cierra ese proceso y vuelve a ejecutar.
4
Frontend: terminal en frontend-angular: npm install (primera vez) y npm start. Abrir http://localhost:4200.
