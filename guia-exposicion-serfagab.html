Planificación simple y cronometrada de la exposición del Sistema Web de Gestión de Compras de SERFAGAB S.A.C. para el curso Desarrollo de Aplicaciones Web I. Orden de exposición: Carlos → Oscar → Manuel → Valerie. Cada sección incluye su bloque de tiempo, las diapositivas que le corresponden, un guion sugerido de qué decir y la frase exacta para entregarle la palabra al siguiente compañero.

3. CARLOS — El negocio y el problema

Tu misión

Abrir la exposición con energía y dejarle al público claro quién es SERFAGAB, qué dolor tiene y qué proponemos. Al terminar tu bloque, todos deben entender el problema aunque no entiendan nada de tecnología todavía.

Slide 1 — Portada (30 seg)

  • Saludo breve: buenos días/tardes profesor y compañeros.
  • Presenten al equipo completo de una sola vez (los 4 nombres) y digan qué curso es.
  • Anuncien el tema: "Sistema Web de Gestión de Compras para SERFAGAB SAC".
  • Mencionen la agenda en una frase: "Veremos primero la empresa y su problema, luego nuestros objetivos, cómo construimos el sistema, y terminaremos con una demostración en vivo".

Slide 2 — Quién es SERFAGAB (1 min)

  • Empresa peruana dedicada a la fabricación de tableros metálicos con integración eléctrica, atendiendo proyectos industriales y comerciales.
  • Citar el lema como gancho: "Creado para dar Soluciones" — y conectar: "irónicamente, sus propias compras eran lo menos resuelto".
  • Cerrar la slide con el reto: como toda empresa en crecimiento, dependen de registros manuales que les restan velocidad y control frente a sus proveedores.

Slide 3 — Diagnóstico (1 min 15 seg)

Recorrer los 4 dolores contándolos como historia (no leer la lista):

  • 1. Registro manual: órdenes y cotizaciones en cuadernos o Excel.
  • 2. Información dispersa: cada área guarda sus propios datos de proveedores.
  • 3. Poco control: no existe historial centralizado de compras.
  • 4. Demoras y errores: el seguimiento manual retrasa la fabricación de los tableros.

Frase puente recomendada: "Imaginen que el área de producción necesita un gabinete urgente: hoy eso significa llamar por teléfono, buscar el número del proveedor en un cuaderno y rezar para que nadie haya duplicado la orden."

Slide 4 — La solución propuesta (1 min 15 seg)

  • Un Sistema Web de Gestión de Compras que centraliza proveedores y órdenes de compra, reemplazando el registro manual por un flujo digital, trazable y rápido.
  • Explicar el flujo nuevo de 4 pasos: el proveedor envía cotización → el sistema registra la orden → compras hace seguimiento en línea → reportes centralizados.
  • Rematar con la comparación: "de cuaderno a plataforma".
Entrega a Oscar: "Ese es el problema que nos planteamos resolver. Para hacerlo bien, primero definimos metas claras, y para explicarlas está Oscar."
2do ponente · ~3 min · Slide 5 (+ módulos)

4. OSCAR — Objetivos y alcance del sistema

Tu misión

Hacer el puente entre el problema que contó Carlos y la parte técnica de Manuel: qué nos propusimos lograr y qué incluye exactamente el sistema. Es el bloque corto: 3 minutos máximo.

Slide 5 — Metas del proyecto (1 min 30 seg)

  • Objetivo general: automatizar la gestión de compras de SERFAGAB mediante una plataforma web que centralice proveedores y órdenes de compra. Dígalo lento, es LA frase del proyecto.
  • Luego las 4 metas específicas, agrupadas de dos en dos:
    1. Automatizar procesos: reducir tareas manuales repetitivas.
    2. Reducir errores: minimizar inconsistencias por doble digitación.
    3. Centralizar información: proveedores y órdenes en una sola fuente de datos.
    4. Mejorar el control: visibilidad y trazabilidad de cada orden.

Módulos del sistema (sin slide propia, ~1 min)

Enumerar de memoria lo que el sistema hace HOY (no prometer cosas futuras):

  • Login de usuarios con roles: administrador y usuario de consulta.
  • Gestión de materiales y tipos de material (crear, editar, listar, buscar, paginar).
  • Gestión de proveedores con validación de RUC, celular y correo.
  • Órdenes de compra con sus detalles, estados (pendiente/enviado/anulado) e historial filtrable por fecha y proveedor.
  • Descarga en PDF de cada orden lista para enviar.
Entrega a Manuel: "Ese es el alcance funcional. Ahora bien, ¿cómo logramos construirlo? Para explicarlo está Manuel."
3er ponente · ~4 min · Slides 6–7

5. MANUEL — Arquitectura y backend

Tu misión

Explicar cómo está construido el sistema de forma que un no-experto lo entienda con el diagrama, pero dando suficientes detalles técnicos para el profesor. Este bloque es el que más impresiona si lo dominas: habla con seguridad de capas y seguridad.

Slide 6 — Arquitectura (2 min)

  • Contar el recorrido de una petición con el diagrama: navegador (Angular) → API REST (Spring Boot) → Controller → Service → Repository → MySQL.
  • Explicar cada capa en una frase sencilla:
    • Controller: recibe las peticiones HTTP del frontend.
    • Service: contiene las reglas del negocio (ej.: calcular el total de una orden).
    • Repository: guarda y consulta los datos en la base.
  • Ojo: esta slide aún dice "Postman → H2". Explicar la versión real: probamos cada endpoint con Postman durante el desarrollo, pero el cliente final es la SPA de Angular y la base definitiva es MySQL.

Slide 7 — Stack tecnológico (1 min)

  • Java 24 + Spring Boot 4: framework del backend y servicios REST.
  • Angular 21 + Bootstrap 5: interfaz web moderna y responsiva.
  • MySQL: base de datos relacional (vía XAMPP).
  • Maven: gestión de dependencias · Git: control de versiones · OpenPDF: reportes PDF · Postman: pruebas de API.

Bonus si llevas el tiempo bien (1 min)

  • Seguridad: contraseñas cifradas con BCrypt, autenticación y roles: solo el administrador crea/edita/elimina; el usuario de consulta solo ve.
  • Datos de prueba: el sistema se auto-puebla al iniciar (DataSeeder) con 16 proveedores, 26 materiales y órdenes de ejemplo, ideal para la demo.
Entrega a Valerie: "Esa es la maquinaria detrás. Lo mejor es verlo funcionar: para la demostración en vivo, con ustedes Valerie."
4ta ponente · ~3.5 min · Slides 8–12, 14–15

6. VALERIE — Demo en vivo + impacto + cierre

Tu misión

La parte más arriesgada y la más memorable: mostrar el sistema vivo y cerrar con broche de oro. Practica esta ruta varias veces hasta poder hacerla en 2 minutos sin dudar.

Ruta de la demo (2 min, con la app corriendo de fondo)

  1. Login como administrador (admin / admin123) — mostrar que entra al dashboard con tarjetas resumen.
  2. Dashboard: señalar KPIs (materiales, proveedores, órdenes) y las últimas órdenes.
  3. Proveedores: registrar uno nuevo en segundos (validaciones en vivo de RUC/celular/email = momento wow).
  4. Órdenes: abrir una orden existente, ver sus detalles y cambiar su estado a ENVIADO.
  5. PDF: descargar la orden en PDF y decir: "este documento sale directo del sistema, listo para enviar al proveedor".
  6. (Opcional si hay tiempo) login con usuario de consulta (user / user123) para mostrar que NO ve botones de administrador.
Regla de oro de la demo: nunca depures errores en vivo. Si algo falla: sonríe, di "esto lo vemos mejor en la captura" y pasa a las screenshots del PPTX (slides 8–11).

Slide 12 — Impacto esperado (45 seg)

Contrastar ANTES vs DESPUÉS mirando al público, no la pantalla: de papel, hojas sueltas y Excel → a un solo sistema con información centralizada, seguimiento completo y procesos más ágiles y confiables.

Slides 14–15 — Conclusiones y gracias (45 seg)

  • Automatización real: flujo digital operable desde el primer día.
  • Base sólida y escalable: la arquitectura permite ampliarlo a otras áreas de la empresa.
  • Control y visibilidad: SERFAGAB por fin tiene control sobre sus compras.
  • Cierre: "Esto fue el Grupo 5. Muchas gracias, quedamos atentos a sus preguntas." (slide de Gracias).
Operación

7. Consejos prácticos y plan B

Antes del día de la exposición

  • Ensayo cronometrado completo, mínimo 1 vez, idealmente 2. Cronometrar a cada quien individualmente también ayuda.
  • Definir quién maneja los slides: recomendado que cada quien avance su propia diapositiva con clic o control remoto, así nadie depende de otro.
  • Levantar el entorno antes de clase: XAMPP (MySQL) arriba, backend corriendo en el puerto 8080, frontend en el 4200, navegador ya abierto en el login. Probar la demo completa 5 minutos antes de entrar.
  • Capturas de pantalla listas (slides 8–11) como plan B por si falla algo en vivo.
  • Proyectar con zoom 125%+ en el navegador para que el texto de la app se lea desde el fondo del aula.

Durante la exposición

  • No leer las diapositivas: son apoyo visual, el contenido va de su boca.
  • Mirar al público (y alternar con el profesor), no a la pantalla ni a la laptop.
  • Las transiciones son parte de la nota: entregar mencionando por nombre al siguiente y recibir retomando lo último que se dijo.
  • Si alguien olvida algo, el siguiente lo rescata con naturalidad: "como mencionaba Carlos…".

9. Posibles preguntas del profesor (y cómo responderlas)

Pregunta probableRespuesta corta sugerida
¿Por qué Spring Boot y no otra tecnología?Es el framework visto en el curso; maduro, con JPA/Hibernate incluido y genera APIs REST rápidamente.
¿Cómo funciona la seguridad?Spring Security + BCrypt para cifrar contraseñas y roles ADMIN/USER que restringen los endpoints; el frontend además oculta los botones según el rol.
¿Qué pasa si dos usuarios editan el mismo material?El material usa versionamiento optimista (@Version): Hibernate rechaza la edición desactualizada evitando pisar cambios.
¿Cómo generan el PDF?Con OpenPDF: se arma el documento en el backend (tabla de detalles, totales) y el endpoint lo devuelve como archivo descargable.
¿Cómo probaron la API?Cada endpoint se validó primero con Postman antes de conectarlo al frontend.
¿Cómo se dividió el trabajo?Todos participamos en desarrollo y pruebas; para la exposición dividimos por fortalezas: negocio (Carlos/Oscar), arquitectura (Manuel) y producto/demo (Valerie).
Reparto de respuestas: acuerden de antemano quién responde qué (Manuel: técnico/backend · Oscar: objetivos/alcance · Carlos: negocio · Valerie: producto/UI). Responder con nombre propio ("esa me toca a mí") transmite equipo organizado.
